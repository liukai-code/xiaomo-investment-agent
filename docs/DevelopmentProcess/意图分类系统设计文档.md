# 意图分类系统设计文档

> 项目：小墨金融投资导学 AI 助手
> 模块：`agent.intent` 包
> 更新日期：2026-07-30

---

## 1. 系统概述

意图分类器是 AI Agent 对话链路的第一环。用户消息进入后，系统需要判断"用户想做什么"，再据此决定：加载哪些工具、是否锁定股票标的、是否启用多步任务规划。

当前采用**规则分类 + 在线实体解析**方案。分类逻辑本身不依赖 LLM 调用，延迟在毫秒级；标的解析需调用东财/新浪 API，耗时约 200-500ms。

### 1.1 分类结果

分类器输出一个 `IntentResult` 对象，包含五个字段：

```java
// IntentResult.java
public record IntentResult(
    IntentType intent,      // 业务意图（用户想分析什么）
    AnalysisDepth depth,    // 分析深度（普通 / 深度）
    double confidence,      // 置信度 0.0-1.0
    ResolvedTarget target,  // 解析出的股票标的（需要标的的意图且解析成功时非 null）
    ToolPolicy policy       // 工具策略
)
```

**业务意图与分析深度分离**：`IntentType` 只描述用户想分析什么（个股、板块、新闻等），`AnalysisDepth` 描述分析强度（普通 / 深度）。"深度分析茅台"拆分为 `intent=STOCK_ANALYSIS, depth=DEEP`，"分析茅台"则是 `intent=STOCK_ANALYSIS, depth=NORMAL`。

### 1.2 工具策略

原先用 `suggestedTools` 的三种状态（null / 空集 / 非空集）表达工具策略，语义隐晦。现改为显式建模：

```java
// ToolPolicyMode.java
public enum ToolPolicyMode {
    ALLOW_LIST,      // 白名单模式 — 只加载 policy.tools 中指定的工具
    DENY_ALL,        // 禁用所有业务工具 — 通用对话模式
    PLANNER_MANAGED  // 由 Planner 管理 — 跳过静态白名单，由 LLM 根据执行计划动态选择工具
}

// ToolPolicy.java
public record ToolPolicy(ToolPolicyMode mode, Set<String> tools) {
    public Set<String> toWhitelist() {
        return switch (mode) {
            case ALLOW_LIST -> tools;
            case DENY_ALL -> Set.of();
            case PLANNER_MANAGED -> null;  // null = 不过滤
        };
    }
}
```

## 2. 意图类型

### 2.1 业务意图枚举

共 8 种业务意图（`IntentType.java`）：

| 枚举值 | 含义 | 典型输入 | 工具策略 |
|--------|------|----------|---------|
| `STOCK_ANALYSIS` | 个股分析 | "分析茅台"、"600519行情" | ALLOW_LIST（全量 A 股工具，13个） |
| `MARKET_NEWS` | 市场新闻 | "今日新闻"、"央行降息影响" | ALLOW_LIST（新闻+搜索，6个） |
| `SECTOR_ANALYSIS` | 板块/行业分析 | "半导体板块怎么样" | ALLOW_LIST（板块相关，8个） |
| `TRADING_SENTIMENT` | 打板/情绪 | "涨停池"、"龙虎榜" | ALLOW_LIST（情绪+打板，5个） |
| `HOLDINGS_QUERY` | 持仓查询 | "我的基金"、"我的持仓" | ALLOW_LIST（持仓工具，4个） |
| `FINANCIAL_CALC` | 金融计算 | "帮我算收益率"、"NPV计算" | ALLOW_LIST（计算器+行情，2个） |
| `DB_QUERY` | 数据库查询 | "执行SQL查询" | ALLOW_LIST（SQL 工具，2个） |
| `GENERAL_CHAT` | 通用对话 | "你好"、"什么是PE" | DENY_ALL（无工具） |

### 2.2 分析深度枚举

```java
// AnalysisDepth.java
public enum AnalysisDepth {
    NORMAL,  // 普通分析 — 单步或少量工具调用即可完成
    DEEP     // 深度分析 — 需要 LLM 多步规划，综合多个数据源
}
```

`DEEP` 深度使工具策略变为 `PLANNER_MANAGED`，跳过静态白名单，由 LLM Planner 根据用户请求动态制定执行计划并选择工具。例如"深度分析茅台"使用 `STOCK_ANALYSIS` 的业务意图确定分析对象，同时通过 `PLANNER_MANAGED` 让 LLM 自主规划多步分析流程。

## 3. 分类策略：两阶段处理

`RuleBasedIntentClassifier.classify()` 分为两个阶段：

### 阶段一：深度提取

检测消息中是否包含深度标记词（"深度分析"、"详细研究"等 12 个模式）。命中则设置 `depth=DEEP`，但**不剥离文本**——保留"分析"等关键词供后续业务分类使用。

### 阶段二：业务意图分类

按固定优先级顺序匹配，命中即返回：

```
用户消息
  │
  ├─ 第一优先级：高特异性意图
  │   ├─ isHoldingsQuery()    → HOLDINGS_QUERY     (confidence=0.95)
  │   └─ isGeneralChat()      → GENERAL_CHAT       (0.9)
  │
  ├─ 第二优先级：金融专业意图
  │   ├─ isSectorAnalysis()   → SECTOR_ANALYSIS    (0.9)
  │   ├─ isFinancialCalc()    → FINANCIAL_CALC     (0.9)
  │   ├─ isMarketNews()       → MARKET_NEWS        (0.85)
  │   ├─ isTradingSentiment() → TRADING_SENTIMENT   (0.9)
  │   └─ isDbQuery()          → DB_QUERY           (0.9)
  │
  ├─ 第三优先级：个股分析（成本最高）
  │   └─ hasAnalysisIntent()  → STOCK_ANALYSIS     (0.85)
  │       └─ 需调用 StockResolver 解析标的，失败则降级
  │
  └─ 兜底
      └─ GENERAL_CHAT (0.5)
```

最终结果合并深度标记：如果 `depth==DEEP`，工具策略强制设为 `PLANNER_MANAGED`。

### 3.1 为什么这样排序

优先级设计的核心原则是**高特异性优先**：

- **持仓查询**放第一位，因为"我的基金"这类消息特征极其明确，不会与其他意图混淆，且置信度最高（0.95）。
- **通用对话**放第二位，是因为"什么是PE"这类概念解释类问题如果排在后面，会被 `hasAnalysisIntent()` 中的关键词误匹配为个股分析。通过在 `isGeneralChat()` 中先拦截，可以避免这个问题。
- **个股分析**放最后，因为它需要调用外部 API 解析标的（东财 suggest API），成本最高。只有当其他意图都没命中、且消息中确实包含分析关键词时才触发。

### 3.2 意图间的歧义处理

实际使用中，用户消息经常跨越多个意图边界。当前的处理方式：

**"半导体板块分析"** — 包含"分析"（ANALYSIS_KEYWORDS）和"板块"（SECTOR_KEYWORDS）。由于 `isSectorAnalysis` 在第二优先级、`hasAnalysisIntent` 在第三优先级，最终分类为 `SECTOR_ANALYSIS`。

**"分析一下今天的新闻"** — 包含"分析"和"新闻"。`isMarketNews` 在第二优先级，`hasAnalysisIntent` 在第三。但 `isMarketNews()` 内部有一个特殊判断：如果同时包含分析关键词和 6 位数字代码，则不排除（可能是个股新闻分析）。由于本消息没有数字代码，最终分类为 `MARKET_NEWS`。

**"茅台概念热度"** — 包含"概念"（SECTOR_KEYWORDS）和"热度"（SENTIMENT_KEYWORDS）。`isSectorAnalysis` 优先级高于 `isTradingSentiment`，最终分类为 `SECTOR_ANALYSIS`。

## 4. 各判断方法的实现细节

### 4.1 isHoldingsQuery — 精确短语匹配

```java
private boolean isHoldingsQuery(String msg) {
    for (String kw : HOLDINGS_KEYWORDS) {
        if (msg.contains(kw)) return true;
    }
    return false;
}
```

关键词列表：`"我的基金"`, `"我的持仓"`, `"看看我的基金"`, `"我的仓位"`, `"养基宝"`, `"我的投资组合"`, `"账户余额"`。

这些是精确的业务短语，误匹配概率极低。

### 4.2 isGeneralChat — 解释句式 + 排除逻辑

```java
private boolean isGeneralChat(String msg) {
    String lower = msg.toLowerCase();
    // 1. 纯问候（精确匹配）
    for (String g : GREETINGS) {
        if (lower.equals(g) || lower.equals(g + "！") || lower.equals(g + "!")) return true;
    }
    // 2. 明确的解释句式（不受分析意图排除）
    for (String p : EXPLANATION_PATTERNS) {
        if (msg.contains(p)) return true;
    }
    // 3. 概念类关键词（排除包含分析意图的情况）
    boolean hasCalcIntent = isFinancialCalc(msg);
    if (!hasCalcIntent) {
        for (String c : CONCEPT_KEYWORDS) {
            if (msg.contains(c) && !hasAnalysisIntent(msg)) return true;
        }
    }
    // 4. 学习类（不含分析意图时）
    for (String l : LEARNING_KEYWORDS) {
        if (msg.contains(l) && !hasAnalysisIntent(msg)) return true;
    }
    return false;
}
```

四层逻辑：

1. **问候匹配**：精确匹配 `"你好"`、`"hi"` 等，区分大小写但兼容中英文感叹号。
2. **解释句式**：包含 `"什么是"`、`"是什么意思"`、`"解释一下"` 等明确的解释请求时，直接判定为通用对话，不受分析意图排除。例如"什么是市盈率"、"什么是PE"都走这条路径。
3. **概念类**：`CONCEPT_KEYWORDS` 中只保留不会与分析意图冲突的纯概念词（如"复利"、"夏普比率"）。PE/PB/ROE/市盈率等指标词已移至 `ANALYSIS_KEYWORDS`，确保"茅台PE是多少"不会被误判为通用对话。同时排除包含分析意图的消息。
4. **学习类**：包含 `"学习"`、`"教程"` 等词时，还要确认不含分析关键词，避免"学习分析茅台"被误判为通用对话。

### 4.3 isMarketNews — 带排除条件的新闻判断

```java
private boolean isMarketNews(String msg) {
    boolean hasNews = false;
    for (String kw : NEWS_KEYWORDS) {
        if (msg.contains(kw)) { hasNews = true; break; }
    }
    if (!hasNews) return false;
    // 如果同时包含个股分析关键词和标的代码，可能是个股新闻分析，走 STOCK_ANALYSIS
    if (hasAnalysisIntent(msg) && CODE_PATTERN.matcher(msg).find()) return false;
    return true;
}
```

这条排除规则处理的是"600519最新消息"这类消息——既包含新闻关键词"最新消息"，又包含分析关键词和股票代码。此时不排除，让它走到 `hasAnalysisIntent()` → `tryResolveStock()`，最终分类为 `STOCK_ANALYSIS`。

### 4.4 hasAnalysisIntent — 分析意图识别

```java
private boolean hasAnalysisIntent(String msg) {
    for (String kw : ANALYSIS_KEYWORDS) {
        if (msg.contains(kw)) return true;
    }
    return false;
}
```

`ANALYSIS_KEYWORDS` 包含约 55 个词，覆盖：分析动作词（"分析"、"研究"、"调研"）、行情查询词（"行情"、"股价"、"涨跌"）、财务指标词（"PE"、"PB"、"ROE"、"市盈率"、"市值"）、数据维度词（"基本面"、"资金面"、"技术面"、"角度"）等。

只要命中任意一个词就返回 true。这个判断是进入标的解析的前置条件。

## 5. 标的解析：tryResolveStock

当业务意图判断为 `STOCK_ANALYSIS` 时，调用 `tryResolveStock()` 方法解析标的。

### 5.1 解析流程

```
用户消息
  │
  ├─ 有6位数字代码？ ──是──→ 用代码调东财 API 反查名称 → 返回 {code, name}
  │
  └─ 否 → stripAnalysisKeywords(保留时间词) → StockResolver 解析
           │
           ├─ 成功 → 返回
           │
           └─ 失败 → stripAnalysisKeywords(剥离时间词) → 再次尝试
                     │
                     ├─ 成功 → 返回
                     └─ 失败 → 降级为 GENERAL_CHAT (0.5)
```

**关键设计**：先用保留时间词的版本尝试解析，保护"今天国际"(300532) 等包含时间词的股票名称。只有原文解析失败后，才剥离时间词重试，处理"今天行情怎么样" → 降级的场景。

### 5.2 关键词剥离：stripAnalysisKeywords

```java
private String stripAnalysisKeywords(String msg, boolean stripTimeWords) {
    String cleaned = msg;
    for (String kw : STRIP_KEYWORDS) {
        cleaned = cleaned.replace(kw, "");
    }
    if (stripTimeWords) {
        for (String kw : TIME_KEYWORDS) {
            cleaned = cleaned.replace(kw, "");
        }
    }
    cleaned = cleaned.replaceAll("[，。？！、\\s]+", "").trim();
    return cleaned;
}
```

`stripTimeWords` 参数控制是否剥离时间词。首次尝试 `false`（保留"今天国际"），失败后重试 `true`（处理"今天行情怎么样"）。

**实际执行示例**：

| 输入 | 首次剥离(保留时间词) | 二次剥离(含时间词) | 结果 |
|------|---------------------|-------------------|------|
| "分析茅台" | "茅台" | — | STOCK_ANALYSIS |
| "今天国际怎么样" | "国际怎么样" | — | STOCK_ANALYSIS(首次成功) |
| "今天行情怎么样" | "行情怎么样"(失败) | ""(空) | GENERAL_CHAT |
| "从基本面资金面三个角度招商银行" | "从三个招商银行" | — | STOCK_ANALYSIS |

### 5.3 StockResolver 标的解析器

代码位置：`StockResolver.java`。纯工具类（私有构造函数），提供静态方法 `resolve(String query, HttpClientService)`。

**解析步骤**：

**Step 1 — 数字代码提取**：正则 `(?<!\d)(\d{6})(?!\d)` 匹配独立的 6 位数字。匹配到后直接用代码查东财 API。

**Step 2 — 中文名称提取**：正则 `[一-龥]{2,}` 匹配连续 2 个以上中文字符。

**Step 3 — 虚词前缀剥离**：使用交替匹配（词语级别）而非字符集合，避免破坏"三一重工"等合法股票名称。

```java
// 使用 (?:从|把|被|对|...) 交替匹配，而非 [从把被对...] 字符集合
private static final Pattern NOISE_PREFIX_PATTERN = Pattern.compile(
    "^(?:从|把|被|对|为|给|让|叫|用|通过|和|与|及|的|了|一|两个|三个|四个|五个|多个|几个|些|所有|全部|每个)+");
```

"从三个招商银行" → "招商银行"。"三一重工" → 不受影响。

**Step 4 — 查询前缀/后缀剥离**：`QUERY_PREFIXES` 包含 20 个分析动作前缀（"深度分析"、"帮我看看"等），`QUERY_SUFFIXES` 包含 23 个评价性后缀（"怎么样"、"值得入手吗"等）。

**Step 5 — 外部 API 查询**：双源查询策略——先东财 suggest API，失败则 fallback 到新浪 suggest API。

**Step 6 — 最佳匹配选择**：三级匹配策略——名称包含输入 > 输入包含名称 > 兜底取第一个。

### 5.4 标的解析失败时的降级策略

```java
// 两次都失败，降级
if (isMarketNews(msg)) {
    return new IntentResult(IntentType.MARKET_NEWS, depth, 0.6, null, ...);
}
return new IntentResult(IntentType.GENERAL_CHAT, depth, 0.5, null, ...);
```

- **STOCK_ANALYSIS 解析失败**：先尝试回退到 MARKET_NEWS（如"分析今天的新闻"解析不出标的但有新闻关键词），否则降级为 GENERAL_CHAT。
- 深度分析的标的解析失败不特殊处理——`STOCK_ANALYSIS + DEEP` 解析失败同样降级，由 LLM Planner 在后续交互中根据上下文确定分析对象。

## 6. 工具策略映射

`IntentToolGroupMap.getPolicy(IntentType, AnalysisDepth)` 根据业务意图和分析深度生成工具策略：

```java
public static ToolPolicy getPolicy(IntentType intent, AnalysisDepth depth) {
    // 深度分析跳过静态白名单，由 Planner 管理工具选择
    if (depth == AnalysisDepth.DEEP) {
        return ToolPolicy.plannerManaged();
    }
    Set<String> tools = GROUP_MAP.getOrDefault(intent, Set.of());
    if (tools.isEmpty() && intent == IntentType.GENERAL_CHAT) {
        return ToolPolicy.denyAll();
    }
    return ToolPolicy.allowList(tools);
}
```

各意图的工具白名单：

```
STOCK_ANALYSIS    → {a_stock_quote, a_stock_report, a_stock_signal, a_stock_capital,
                      a_stock_news, a_stock_limit_up, a_stock_option, a_stock_sentiment,
                      market_data, financial_calculator, getAnalysisReport,
                      fetchWebpage, fetchArticleContent}  // 13个
MARKET_NEWS       → {a_stock_news, a_stock_signal, a_stock_limit_up,
                      market_data, fetchWebpage, fetchArticleContent}  // 6个
SECTOR_ANALYSIS   → {a_stock_signal, a_stock_report, a_stock_news, a_stock_limit_up,
                      a_stock_sentiment, market_data, fetchWebpage, fetchArticleContent}  // 8个
TRADING_SENTIMENT → {a_stock_limit_up, a_stock_signal, a_stock_sentiment,
                      a_stock_news, market_data}  // 5个
HOLDINGS_QUERY    → {getMyHoldings, getMyAccountSummary, market_data, a_stock_quote}  // 4个
FINANCIAL_CALC    → {financial_calculator, market_data}  // 2个
DB_QUERY          → {getDatabaseSchema, executeQuery}  // 2个
GENERAL_CHAT      → DENY_ALL（不加载业务工具）
任意意图 + DEEP   → PLANNER_MANAGED（由 Planner 管理）
```

设计原则：
- 通用对话不加载工具，强制 LLM 用自身知识回答，避免不必要的工具调用开销。
- 深度分析使用 `PLANNER_MANAGED`，跳过静态白名单，由 LLM Planner 根据执行计划动态选择工具。
- MCP 搜索工具（如 `bailian_web_search`）由 `AgentLoopImpl` 在过滤时特殊处理，始终保留，不受意图白名单限制。

## 7. 与其他模块的交互

### 7.1 AgentLoopImpl 中的调用链

```java
// AgentLoopImpl.java（同步路径，流式路径类似）
IntentResult intentResult = intentClassifier.classify(message);
IntentResult.ResolvedTarget target = intentResult.target();

// 如果意图分类器未启用，回退到原有逻辑
if (intentResult.confidence() == 0
        && intentResult.policy().mode() == ToolPolicyMode.PLANNER_MANAGED) {
    target = ContextBuilder.toResolvedTarget(contextBuilder.resolveStockFromMessage(message));
}

// 自主任务规划（深度分析始终触发，普通请求按复杂度判断）
PlanContext planContext = maybePlan(message, intentResult.intent(),
        intentResult.depth(), target, allWrappedCallbacks);

// 构建上下文（注入标的锁定、意图提示、执行计划）
List<Message> context = contextBuilder.buildContext(..., intentResult.intent(), ..., planContext);

// 工具过滤
Set<String> intentToolWhitelist = intentResult.policy().toWhitelist();
List<ToolCallback> enabledTools = toolFilter.filter(allWrappedCallbacks, mcpToolNames,
        intentToolWhitelist, target);
```

### 7.2 ContextBuilder 中的意图注入

`ContextBuilder.buildContext()` 根据意图类型向 system prompt 追加不同的任务约束：

- `MARKET_NEWS`：提示使用新闻工具，不要展开成个股分析
- `SECTOR_ANALYSIS`：提示使用板块工具，不需要锁定个股
- `TRADING_SENTIMENT`：提示使用打板/情绪工具
- `HOLDINGS_QUERY`：提示使用持仓查询工具
- `FINANCIAL_CALC`：提示使用金融计算器

### 7.3 TaskPlanner 中的规划触发

`TaskPlanner.needsPlanning(String message, IntentType intent, AnalysisDepth depth)` 根据意图类型和分析深度决定是否启用多步规划：

```java
public boolean needsPlanning(String message, IntentType intent, AnalysisDepth depth) {
    if (!planningProperties.enabled()) return false;
    if (depth == AnalysisDepth.DEEP) return true;  // 深度分析始终触发

    return switch (intent) {
        case GENERAL_CHAT, FINANCIAL_CALC, DB_QUERY, HOLDINGS_QUERY -> false;
        case STOCK_ANALYSIS -> hasMultiDimensionKeywords(message);
        case MARKET_NEWS -> hasMultiTopicKeywords(message);
        case SECTOR_ANALYSIS -> hasComparisonKeywords(message);
        case TRADING_SENTIMENT -> false;
    };
}
```

## 9. 已知局限与后续改进方向

### 9.1 规则匹配的固有局限

- **关键词覆盖不全**：用户表达方式多样，"帮我瞅瞅茅台咋样"中的"瞅瞅"、"咋样"不在关键词列表中，会被降级为 GENERAL_CHAT。规则方案需要持续补充关键词。
- **上下文无关**：每次分类独立进行，不考虑对话历史。如果用户先说"茅台"，再说"它的 PE 呢"，第二句无法关联到茅台。
- **歧义消解能力有限**：依赖优先级硬排序处理歧义，无法理解语义层面的优先级。

### 9.2 标的解析的局限

- **多标的不支持**："对比茅台和五粮液"只能解析出第一个匹配的标的。
- **非 A 股不覆盖**：StockResolver 只查沪深 A 股（东财 + 新浪），北交所、港股、美股标的会解析失败。
- **名称模糊匹配不可靠**：东财 suggest API 返回的候选结果有限（最多 5 条），冷门股票可能查不到。
- **网络依赖**：标的解析需要调用外部 API，网络异常时会降级。

### 9.3 可能的改进方向

- 引入 LLM 辅助分类：对规则无法确定的 case（confidence < 0.6），调用小模型做二次判断。
- 对话上下文感知：在 `IntentResult` 中携带上一轮的标的信息，支持指代消解。
- 关键词动态维护：将关键词列表外置到配置文件或数据库，支持运营热更新。
- 多意图支持：将 `IntentResult` 扩展为支持主意图 + 次要意图，处理"半导体板块今天的新闻和情绪"这类跨意图请求。
- 多标的支持：将 `target` 扩展为 `List<ResolvedTarget>`，支持"对比茅台和五粮液"这类比较请求。
