# 工具开关管理机制

## 概述

系统提供了一套完整的 AI Agent 工具启停管理机制，允许管理员通过 Web 管理页面动态控制哪些工具对模型可用。禁用的工具不会出现在模型的 tool list 中，模型完全感知不到被禁用的工具，从源头避免无效调用。

## 核心组件

### 1. ToolConfigService — 配置存储

**路径**: `tool/config/ToolConfigService.java`

负责工具启停状态的持久化存储，底层使用 Redis Hash。

| 方法 | 说明 |
|------|------|
| `initDefaults(List<String>)` | 应用启动时调用，将所有工具名写入 Redis，默认全部 `"true"`。仅首次执行（Redis 为空时才写入），已有的配置不会被覆盖 |
| `isEnabled(String)` | 查询单个工具是否启用，Redis 中不存在则默认 `true` |
| `setEnabled(String, boolean)` | 设置工具启用/禁用状态 |
| `listAll()` | 返回所有工具的 `{name: boolean}` 映射，一次 `HGETALL` |

**Redis 数据结构**:

```
Key:   agent:tool:config (Hash)
Field: compoundInterest  → "true"
Field: getAShareQuote    → "true"
Field: executeQuery      → "false"
...
```

**初始化逻辑**: `initDefaults()` 使用 `volatile + synchronized` 双重检查锁保证只执行一次。只有当 Redis Hash 为空时才写入默认值，管理员已修改过的配置在应用重启后不会丢失。

### 2. ToolEnabledCheckWrapper — 调用拦截器（兜底防御）

**路径**: `tool/config/ToolEnabledCheckWrapper.java`

实现 `ToolCallback` 接口的装饰器，包装原始工具。在 `call()` 方法中检查工具是否启用：

- **启用**: 委托给原始工具执行
- **禁用**: 返回提示文本 `"该工具已被管理员禁用，无法使用。请直接用自身知识回答用户问题。"`，不执行实际逻辑

这是一个**兜底机制**。正常情况下，被禁用的工具在请求阶段就被过滤掉了，不会到达 wrapper。wrapper 的存在是为了防御绕过过滤的极端情况。

### 3. ToolConfigController — REST API

**路径**: `tool/config/ToolConfigController.java`

| 端点 | 方法 | 说明 |
|------|------|------|
| `GET /api/auth/tools` | `listTools()` | 返回所有工具及其启用状态 `Map<String, Boolean>` |
| `PUT /api/auth/tools/{name}?enabled={bool}` | `setEnabled()` | 设置指定工具的启用/禁用状态 |

### 4. admin.html — 管理后台

**路径**: `src/main/resources/admin/admin.html`

纯静态 HTML 页面，通过 fetch 调用上述 API 实现：

- **加载时**: `GET /api/auth/tools` 获取所有工具列表，渲染卡片网格
- **切换时**: `PUT /api/auth/tools/{name}?enabled=true/false`，即时生效
- **展示信息**: 工具英文名、中文描述、分组图标（calc/market/data/web/file）、启用/禁用状态、统计数据

前端 `TOOL_META` 对象维护了所有工具的中文描述和分组信息，需要与后端注册的工具保持同步。

## 工具注册流程

### AgentLoopImpl（单 Agent 对话）

**构造阶段**（应用启动时执行一次）:

1. 通过 `MethodToolCallbackProvider` 将 7 个工具 Bean 转为 `ToolCallback[]`
2. 遍历每个 `ToolCallback`，用 `ToolEnabledCheckWrapper` 包装
3. 同样包装 MCP 外部工具（如百炼搜索）
4. 将所有包装后的 callback 存入 `allWrappedCallbacks` 字段
5. `ChatClient` **不设置** `defaultToolCallbacks`（不再把全部工具注册为默认）
6. 调用 `toolConfigService.initDefaults(toolNames)` 初始化 Redis 默认配置

**请求阶段**（每次 chat/chatStream 调用）:

1. 一次 `HGETALL` 从 Redis 获取所有工具的启用状态
2. 在内存中过滤出 `enabled=true` 的工具名集合
3. 从 `allWrappedCallbacks` 中筛选出启用的 `ToolCallback` 列表
4. 通过 `prompt.tools(filteredCallbacks)` 只把启用的工具传给模型
5. 模型只能看到和调用启用的工具

```java
// 请求时过滤逻辑
Set<String> enabledNames = toolConfigService.listAll().entrySet().stream()
        .filter(Map.Entry::getValue)
        .map(Map.Entry::getKey)
        .collect(Collectors.toSet());
List<ToolCallback> enabledTools = allWrappedCallbacks.stream()
        .filter(cb -> enabledNames.contains(cb.getToolDefinition().name()))
        .toList();

chatClient.prompt()
        .messages(context)
        .tools(enabledTools.toArray(new ToolCallback[0]))  // 只传启用的工具
        .options(options)
        .call();
```

### WorkflowAgentFactory（多 Agent 工作流）

工作流场景下，工具过滤有两层：

1. **角色过滤**: 每个 Agent 角色（Analyst、Trader 等）有预定义的 `toolNames()` 集合，只绑定该角色需要的工具
2. **启停过滤**: 被 `ToolEnabledCheckWrapper` 包装，即使角色允许但被管理员禁用的工具也会被拦截

与 `AgentLoopImpl` 的区别：工作流的工具过滤主要靠 wrapper（调用时拦截），而非请求时从 tool list 中移除。这是因为工作流中每个节点独立构建，工具列表在节点创建时就确定了。

## 两层防御机制

| 层级 | 位置 | 机制 | 作用 |
|------|------|------|------|
| 第一层（主） | `AgentLoopImpl.chat()` / `chatStream()` | 请求时过滤，不传禁用工具给模型 | 模型看不到禁用工具，避免无效调用 |
| 第二层（兜底） | `ToolEnabledCheckWrapper.call()` | 调用时检查 Redis | 防止绕过过滤直接调用被禁用工具 |

## 数据流

### 管理员切换工具开关

```
admin.html  →  PUT /api/auth/tools/{name}?enabled=false
           →  ToolConfigController.setEnabled()
           →  ToolConfigService.setEnabled()
           →  Redis HSET agent:tool:config {name} "false"
           ←  返回成功
           →  前端即时更新 UI 状态
```

### 用户发起对话（工具已禁用）

```
用户消息  →  AgentLoopImpl.chat()
         →  toolConfigService.listAll()  一次 HGETALL
         →  内存过滤: enabledNames = {"compoundInterest", "getAShareQuote", ...}
         →  allWrappedCallbacks 中筛选启用的工具
         →  prompt.tools(仅启用的工具)  发给模型
         →  模型只能看到启用的工具，不会尝试调用被禁用的工具
```

### 用户发起对话（工具已禁用，兜底场景）

```
假设某种绕过导致禁用工具仍被传给模型:
模型调用被禁用工具  →  ToolEnabledCheckWrapper.call()
                    →  configService.isEnabled() == false
                    →  返回 "该工具已被管理员禁用"
                    →  模型收到提示，用自身知识回答
```

## 注意事项

1. **即时生效**: 管理员切换工具后，下一次对话请求即生效，无需重启服务
2. **配置持久化**: 工具启停状态存储在 Redis 中，应用重启后配置保留
3. **默认全启用**: 首次启动时所有工具默认启用，只有 Redis 为空才写入默认值
4. **generateTitle 不受影响**: 生成对话标题时不传工具（不需要工具调用能力）
5. **前端同步**: `admin.html` 的 `TOOL_META` 需要与后端注册的工具名保持一致，新增工具时需同步更新
