# 深度分析工作流 — 标的漂移问题现状总结

## 一、当前防护机制

已实现五层防护：

| 层级 | 机制 | 文件 | 作用 |
|------|------|------|------|
| L0 | 标的解析门控 | `StockResolver` | 用户输入名称 → 解析为确定的 code+name |
| L1 | 状态锁定 | `WorkflowState` | `resolvedStockCode` 全局只读 |
| L2 | Prompt 约束 | `AnalystNode.buildStockTargetLine()` | 9 条硬约束 + 推理边界 + 当前日期 |
| L3 | 工具入参 Guard | `MaxToolCallManager` | 拦截错误 stockCode + 自动注入缺失参数 |
| L4 | 工具返回过滤 | `MaxToolCallManager` | 标的标识头 + 当前日期 + 行级硬过滤 |

## 二、仍然存在的漂移现象

尽管五层防护全部生效，以下漂移仍在发生：

### 现象 A：标的替换

```
用户输入: 分析亨通光电（600487）
技术分析师输出: 贵州茅台（600519）分析报告
基本面分析师输出: 贵州茅台（600519）深度分析报告
舆情分析师输出: 2024年1月A股市场热点板块分析报告（完全无关）
```

### 现象 B：日期错乱

```
当前日期: 2026年7月5日
舆情分析师输出: "2025年1月20日 A股市场热点板块与涨停股分析报告"
基本面分析师输出: "报告日期：2026年3月25日"
```

### 现象 C：工具调用失败后 fallback 到训练知识

```
LLM: "我将为您获取亨通光电（600487）的数据"
（工具调用失败或未调用）
LLM: "基于我已获取的数据，我将为您提供贵州茅台（600519）的深度分析报告"
（实际没有获取任何数据，完全使用训练知识生成）
```

## 三、根因分析

### 3.1 LLM 训练偏差（核心原因）

贵州茅台是 LLM 训练数据中出现频率最高的分析标的。当 LLM 面临以下情况时，会自动 fallback 到茅台：

- 工具调用失败，没有实时数据
- 工具返回数据格式不熟悉，LLM 不知道如何解读
- 上下文过长，早期的标的锁定信息被"遗忘"
- 多轮工具调用后，LLM 的注意力漂移

**这是 LLM 固有的训练偏差，无法通过 prompt 或工具层完全消除。**

### 3.2 Prompt 约束的局限性

当前 prompt 约束（9 条硬约束）存在以下局限：

| 约束 | 实际效果 | 问题 |
|------|----------|------|
| "禁止分析其他股票" | LLM 有时遵守 | 长上下文后约束力衰减 |
| "禁止使用训练知识" | LLM 经常违反 | 训练知识是 LLM 的默认行为 |
| "报告日期必须为今天" | LLM 有时遵守 | 会使用训练数据中的日期 |
| "工具失败必须重试" | LLM 有时遵守 | 多次失败后直接放弃 |

### 3.3 工具层防护的局限性

| 防护 | 实际效果 | 问题 |
|------|----------|------|
| stockCode 自动注入 | 工具能正常执行 | LLM 可能忽略返回数据 |
| 标的标识头 | LLM 能看到 | LLM 选择性忽略 |
| 行级硬过滤 | 有效移除外来数据 | 全市场工具（热榜等）过滤后可能无有效数据 |
| 入参 scope guard | 有效拦截错误代码 | LLM 可能不调用工具 |

### 3.4 舆情分析师的特殊问题

舆情分析师的问题最严重，因为它使用的工具（`thsHotList`、`emHotRank`）返回的是**全市场数据**，不是个股数据：

- `thsHotList` → 全市场热门股票排行
- `emHotRank` → 全市场人气排行
- `emConceptHit` → 个股概念命中（唯一个股级工具）

LLM 拿到全市场数据后，无法从中提取目标标的信息，于是用训练知识编造报告。

## 四、已尝试的所有修复

| 修复 | 效果 | 说明 |
|------|------|------|
| StockResolver 名称解析 | ✅ 有效 | 名称能正确解析为代码 |
| WorkflowState 标的锁定 | ✅ 有效 | 状态层无漂移 |
| Prompt 9 条硬约束 | ⚠️ 部分有效 | LLM 偶尔遵守 |
| 推理边界约束 | ⚠️ 部分有效 | LLM 仍会引用其他公司 |
| stockCode 自动注入 | ✅ 有效 | 工具不再因缺参数报错 |
| 当前日期自动注入 | ✅ 有效 | date/tradeDate 参数正确 |
| 工具返回标识头 | ⚠️ 部分有效 | LLM 看到但可能忽略 |
| 行级硬过滤 | ✅ 有效 | 外来数据被移除 |
| 错误信息优化 | ✅ 有效 | 参数错误时提示更清晰 |

## 五、可能的进一步改进方向

### 方向 1：工具层强制（最可靠）

**思路**：不依赖 LLM 选择工具，由系统自动预取关键数据并注入到 prompt 中。

```
系统自动执行:
1. 调用 tencentQuote(stockCodes="600487") → 注入行情数据
2. 调用 baiduKline(stockCode="600487") → 注入K线数据
3. 调用 stockReport(stockCode="600487") → 注入研报数据
4. 将所有数据注入到 LLM 的 prompt 中

LLM 只需要: 基于已注入的数据生成分析报告
```

**优点**：彻底消除工具调用失败和标的漂移
**缺点**：失去 LLM 自主选择工具的灵活性

### 方向 2：输出校验层

**思路**：在 LLM 输出后、返回用户前，检查输出内容是否包含目标标的。

```
LLM 输出 → EntityChecker
  → 检查是否包含目标代码（600487）
  → 检查是否包含其他代码（600519）
  → 检查日期是否为今天
  → 不通过 → 要求 LLM 重新生成
```

**优点**：兜底防护
**缺点**：增加延迟，LLM 可能反复生成错误内容

### 方向 3：模型级约束

**思路**：使用 function calling 的 strict mode，强制 LLM 只能输出结构化数据。

```
输出格式:
{
  "stock_code": "600487",
  "stock_name": "亨通光电",
  "date": "2026-07-05",
  "analysis": { ... }
}
```

**优点**：结构化输出无法包含错误标的
**缺点**：需要大幅重构输出格式

### 方向 4：多模型投票

**思路**：多个 LLM 独立分析，投票选出一致结论。

```
Model A → 分析亨通光电 → 报告 A
Model B → 分析亨通光电 → 报告 B
Model C → 分析亨通光电 → 报告 C

Voter → 选择标的一致的报告
```

**优点**：降低单模型偏差
**缺点**：成本翻倍

## 六、结论

当前标的漂移的根本原因是 **LLM 的训练偏差** — 贵州茅台是训练数据中最高频的分析标的，LLM 在缺乏可靠数据时会自动 fallback 到它。

五层防护（解析门控 + 状态锁定 + Prompt 约束 + 工具 Guard + 返回过滤）已经将漂移概率从"几乎必然"降低到"偶尔发生"，但无法完全消除。

**最可靠的解法是方向 1（工具层强制预取）**：不依赖 LLM 自主调用工具，由系统自动获取数据并注入 prompt，LLM 只负责基于已获取的数据生成报告。这从根本上消除了"LLM 不调用工具"和"LLM 调用错误工具"两个最大的漂移来源。
